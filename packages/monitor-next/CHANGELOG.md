# @accessible-so/monitor-next

## 0.2.0

- Component attribution now targets Next 16.4. The SWC plugin is rebuilt on `swc_core` 79 (`swc_ecma_ast` 29, `swc_plugin_runner` 34), which is what Next 16.4.0–16.4.3 link; 0.1.0's wasm, built for Next 16.3's `swc_ecma_ast` 25, fails `next build` on 16.4.
- `withAccessible` now admits only stable Next 16.4.x. 0.1.0 admitted any Next 16, but Next changes its SWC AST between minors (16.2 links `swc_ecma_ast` 20, 16.3 links 25), so the plugin also failed the build on 16.0–16.2. On every other version, prereleases included, it prints `[accessible] component attribution needs Next 16.4.x (found <version>); building without it` and returns the config untouched. On Next 16.3, stay on 0.1.0 to keep attribution.
- Route patterns, both components and the loader are unchanged and still work across the whole peer range (`next >=13.4 <17`). Verified end to end, under both `next build --webpack` and `next build --turbopack`, against Next 16.4.1.

## 0.1.0

- The loader comes from `https://accessible.so/rum/loader.js`, or the `src` prop to self-host it; a custom `endpoint` serves the loader too. `data-endpoint` is rendered only for a non-default endpoint.
- `routePatternFor(pathname, params)` and `RouteMap` — reconstructs the route pattern behind a concrete pathname (`/blog/[slug]`, not `/blog/hello-world`) from the params the App Router already resolved, and keeps a bounded (default 50) LRU of every path the visitor has been on so a finding raised after a client-side navigation away still resolves to a pattern when its beacon is sent.
- `createNextAdapter(map)` and `registerAdapter(adapter)` — build a `CollectorAdapter` (`@accessible-so/monitor-core`) backed by the map, and publish it on `window.__accessibleAdapter`, the slot the engine reads lazily on every attribution lookup.
- `AccessibleMonitor` — the App Router component. Render once in the root layout: it registers the adapter, keeps the route map current on every navigation, and renders the loader `<Script>`. It never starts the engine itself; sampling is still the loader's decision. The map is keyed on `window.location.pathname` — the path the collector looks a pattern up by — rather than on `usePathname()`, so `basePath`, `trailingSlash` and i18n locale prefixes all resolve; the pattern itself stays the app route (`/products/[slug]`, never `/x/products/[slug]`).
- `AccessibleMonitorPages` — the Pages Router counterpart. Render once in `_app`; reads `router.pathname` directly, since the Pages Router already hands over the pattern with no segment-matching needed, and keys it on `window.location.pathname` like the App Router component. Rendered outside a Pages Router context, where `useRouter()` is null, it registers nothing and still renders the loader rather than throwing into the host's render.
- `withAccessible(nextConfig, options?)` — wraps `next.config` to register the build-time component-attribution SWC plugin. It checks that `swc/plugin.wasm` is actually on disk first, and when it is not, prints one `[accessible] swc/plugin.wasm not found` line and returns the config untouched — Next resolves every `experimental.swcPlugins` entry with `require.resolve`, so registering a plugin that was never built would fail the whole `next build`. `{ componentAttribution: false }` (or no Rust toolchain, no `plugin.wasm`) leaves everything else working; attribution is honestly `null`. Registers the plugin by its package specifier (`@accessible-so/monitor-next/swc`), the only form that resolves under both webpack and Turbopack — an absolute path to `plugin.wasm` builds under webpack but Turbopack refuses to resolve it. A function config (`export default (phase) => ({...})`) is called and re-wrapped rather than spread, which would have discarded it.
- The SWC plugin itself (`crates/swc-plugin-accessible`, built by `node scripts/build-swc.mjs`), shipped inside this package as `swc/plugin.wasm`: stamps the outermost host element a named function component returns with `data-a11y-component`/`data-a11y-source`, so a finding can be attributed back to the component that rendered it. `data-a11y-source` is at most `<parent dir>/<file>:<line>`, and drops to the file name alone — or to nothing — rather than emitting a path that would be truncated on the wire or that would carry a home-directory name. See the package README's "What the plugin stamps and what it skips" and the crate's own README for the full rule table and known limits.
- Peer dependencies: `next >=13.4 <17`, `react >=18`. Verified end to end (route patterns, client-side navigation, cross-origin beacon delivery, and component attribution under both `next build --webpack` and `next build --turbopack`) against Next 16.3.5's App Router; the Pages Router component is unit-tested only, not exercised in a browser.
- Component attribution requires Next 16. The SWC plugin is a wasm module that exchanges a serialized AST with its host in a layout fixed by the `swc_core` both were built against; ours is `swc_core` 73, which is what Next 16 links, and Next 15 links 35. Loading the wasm on another major would fail the build rather than degrade, so `withAccessible` reads the resolved `next/package.json` and, outside Next 16, prints `[accessible] component attribution needs Next 16 (found <version>); building without it` and returns the config untouched — the same graceful path a missing `plugin.wasm` takes. Route patterns, both components and the loader are unaffected across the whole peer range.
